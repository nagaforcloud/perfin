# Google Login — Design Spec

**Date:** 2026-05-07
**Status:** Approved by user, ready for implementation planning
**Scope:** Add Google OAuth as a sign-up / sign-in option for the web app, alongside the existing email-and-password flow.

---

## 0. Summary

Add a "Continue with Google" button to `/login` and `/signup`. First-time Google sign-ups create a `users` row with `password_hash = null` and run the existing 3-step onboarding (Welcome → Locale → Connect). Existing email-and-password users who click Google with a matching email auto-link providers (`allowDangerousEmailAccountLinking: true`). No new tables; one column nullability migration; one new shared button component. Roughly 6-8 implementation tasks.

## 1. Brainstorming decisions (binding)

| # | Question | Decision |
|---|---|---|
| 1 | What happens when an existing email user signs in with Google? | **A** — Auto-link by email (`allowDangerousEmailAccountLinking: true`). Email is the identity. |
| 2 | First-time Google sign-up flow | **A** — Same 3-step onboarding as credentials sign-up. |
| 3 | Architectural approach | **A** — Minimal: keep JWT sessions, manual user insert in `signIn` callback, no Auth.js Drizzle adapter swap. |

## 2. End-to-end flow

```
/login or /signup
    │ user clicks "Continue with Google"
    ▼
/api/auth/signin/google              (Auth.js handles redirect)
    │
    ▼
Google OAuth consent screen
    │ user approves
    ▼
/api/auth/callback/google            (Auth.js callback)
    │
    ├── New email?       → signIn callback inserts users row (passwordHash=null)
    │                       redirect → /onboarding/welcome
    │
    └── Existing email?  → providers auto-link via allowDangerousEmailAccountLinking
                           redirect → /app
```

## 4. `signIn` callback contract

```ts
async signIn({ account, profile }) {
  if (account?.provider !== 'google') return true;        // credentials path unchanged
  if (!profile?.email) return false;
  if ((profile as { email_verified?: boolean }).email_verified === false) return false;

  const email = profile.email.toLowerCase();
  const [existing] = await db.select().from(users).where(eq(users.email, email));
  if (!existing) {
    await db.insert(users).values({ email, passwordHash: null, plan: 'free' });
  }
  return true;
}
```

The `redirect` callback decides post-auth landing by checking the just-resolved user's `createdAt`: if within the last 30 seconds, treat as new and route to `/onboarding/welcome`; otherwise `/app`.

## 5. Edge cases

| Case | Behaviour |
|---|---|
| New Google sign-up | Insert user, redirect to onboarding. |
| Existing credentials user clicks Google | Auto-link via `allowDangerousEmailAccountLinking`; redirect to `/app`. |
| Google email unverified | `signIn` returns `false`; user lands on `/login?error=AccessDenied`. Banner shown. |
| User cancels Google consent | Auth.js redirects to `/login?error=OAuthSignin`. Banner shown. |
| Google / network error | Same banner pattern, generic message. |
| `GOOGLE_CLIENT_ID` not set in env | Provider not registered (existing gate). Button is conditionally NOT rendered on login/signup. No broken click. |
| Existing JWT session + new Google click | Auth.js no-ops; lands on `/app`. |

## 6. Configuration

User must perform a one-time Google Cloud Console setup:

1. Visit <https://console.cloud.google.com>, create / select a project.
2. APIs & Services → Credentials → Create Credentials → OAuth client ID.
3. Application type: **Web application**. Name: `Perfin`.
4. Authorized redirect URI: `<AUTH_URL>/api/auth/callback/google` (e.g. `http://localhost:3000/api/auth/callback/google` for dev).
5. Save. Copy Client ID + Client Secret into `.env`:
   ```
   GOOGLE_CLIENT_ID=...
   GOOGLE_CLIENT_SECRET=...
   ```
6. Restart `pnpm dev`.

These two env vars are already documented in `.env.example` from earlier phases. The README will gain a step-by-step subsection.

## 7. Testing

- **Unit (Vitest, `apps/web/tests/auth.test.ts`)** — 4 tests for the `signIn` callback covering: (a) verified-Google new user creation, (b) verified-Google existing user no-op, (c) unverified-Google rejection, (d) credentials-provider passthrough.
- **E2E (Playwright)** — extend `happy-path.spec.ts`. When `process.env.GOOGLE_CLIENT_ID` is set, assert the "Continue with Google" button is visible on `/login` and `/signup`. We do not drive the actual Google OAuth flow (would require a fixture Google account); the visible-button assertion proves the wiring without a real round-trip.

## 8. Risks

- **`allowDangerousEmailAccountLinking`** — accepted in brainstorming Question 1. Mitigation (locking down via a Settings → Account page that lets users review connected providers and set a password) is intentionally deferred. If a Google account is stolen and the user has Perfin tied to it, that's the user's surface area to protect.
- **Migration safety** — making `password_hash` nullable is non-destructive; existing rows keep their hashes; new Google-only rows store `null`.

## 9. Out of scope (deferred)

- Settings → Account page (provider list + password set/unset + provider unlink). Tracked as a future story.
- Other OAuth providers (GitHub, Apple, Microsoft). Adopting `@auth/drizzle-adapter` becomes worthwhile when adding the second provider.
- Profile picture / avatar from Google's `profile.picture` claim. Perfin has no avatar UI today.
- Workspace-only restriction (`hd` claim). Perfin is a consumer SaaS; any Google account is fine.
